## The Amnesia Problem

AI agents have infinite recall and zero continuity.

They'll recite conversations from last month word-for-word, but they wake up every session with complete workflow amnesia. No sense of what's urgent, what's blocked, what's ready to work on. No understanding of how tasks connect to each other or why they exist.

It's like working with the world's smartest intern who has anterograde amnesia. Brilliant at executing any individual task you give them, completely unable to maintain the thread of what you're building together.

The usual solutions miss the point. Task lists are static. Project management tools are built for humans clicking in browsers, not agents that need structured context in milliseconds. GitHub issues are scattered across repositories. Linear tickets live in silos.

What agents need isn't more sophisticated memory. They need a *dependency graph*. A map of what can be done now, what's waiting on what, and most importantly — *why*.

That's what Beads gives them.

## What Beads Actually Is

Issues chained together like beads on a string.

Each bead has dependencies: what it blocks (forward dependencies), what blocks it (backward dependencies). Local-first, Git-friendly, SQLite-backed. CLI-native because that's where agents live.

The name comes from how dependencies connect. You're not managing isolated tasks — you're threading together a workflow where each completed bead automatically unblocks the next ones in the chain.

Here's my current chain for the pronoia redesign:

```bash
$ bd tree noia-abc123
pronoia redesign epic
├── noia-def456 "draft old posts" ✅ DONE
│   └── noia-ghi789 "write new articles" 🔄 IN_PROGRESS
│       └── noia-jkl012 "complete content overhaul" ⏳ BLOCKED
└── noia-mno345 "finalize brand guidelines" 🔄 IN_PROGRESS
    └── noia-ghi789 "write new articles" 🔄 IN_PROGRESS
```

See how it works? The "write new articles" task depends on both drafting old posts AND finalizing brand guidelines. Until both are done, the epic stays blocked. But the moment I close those dependencies, the next tasks automatically become available.

The agent doesn't need to understand my entire content strategy. It just needs to run `bd ready` and see what's unblocked right now.

## The Four Commands That Change Everything

### bd ready — The Agent's Daily Standup

```bash
$ bd ready
noia-def456  P1  draft old posts
noia-mno345  P1  finalize brand guidelines  
noia-pqr678  P2  fix responsive nav bug
```

This is what my agent sees when it starts a session. Not everything I've ever planned. Just what's ready to work on right now. No dependencies blocking it. No context needed beyond what's in the task description.

Sub-100ms response time. The agent knows exactly where to start.

### bd show `<id>` — The Full Context Download

```bash
$ bd show noia-def456
Title: draft old posts
Status: READY
Priority: P1
Labels: content, pronoia

Description:
Go through old pronoia posts and create drafts for rewriting. Focus on 
posts from 2024 that got good engagement but need voice updates.

Comments:
- Need to maintain core ideas but update for 2026 perspective
- Check analytics for top performers first
- Save originals in _archive/ folder

Dependencies:
Blocks: noia-ghi789 (write new articles)
```

The agent gets the WHY, not just the WHAT. Context. History. The intention behind the work. Everything it needs to execute intelligently instead of mechanically.

### bd dep add/tree — Building the Chain

```bash
$ bd dep add noia-ghi789 noia-def456  # ghi789 depends on def456
$ bd dep add noia-jkl012 noia-ghi789  # jkl012 depends on ghi789
```

This is where the magic happens. The agent understands that finishing the blog drafts unblocks writing new articles, which unblocks the epic completion. It sees the chain reaction its work will trigger.

When I close `noia-def456`, the system automatically recalculates what's ready. No manual updates. No project manager moving tickets around. The dependency graph handles the flow.

### bd close — The Cascade Effect

```bash
$ bd close noia-def456
Closed: draft old posts
Unblocked: noia-ghi789 (write new articles)
```

One command. Marks the task done, automatically unblocks everything that was waiting on it, updates the ready queue. The agent's next `bd ready` call shows different available work.

This is the compound effect in action. Each completion automatically unlocks the next layer of possibilities.

## Why Not Linear? Why Not Jira?

Because those tools are built for humans clicking in browsers.

Linear is beautiful for product teams doing sprints. Jira is powerful for enterprise workflows. GitHub Issues are perfect for open source collaboration. But they're all designed around the assumption that intelligent humans will read, interpret, and contextualize tasks.

Agents need structured context they can parse in milliseconds. CLI-first interfaces they can script around. Local-first data they can query without API calls. Git-friendly formats they can version and sync.

`bd ready` takes 80ms and returns exactly what's actionable right now. A Linear API call takes 300ms and returns everything in your sprint. An agent doesn't need to see everything — it needs to see what's *ready*.

The dependency modeling is different too. Traditional tools model dependencies as loose relationships. Beads models them as strict blockers. A task is either ready (no blockers) or it's not (has blockers). This binary makes agent decision-making trivial.

Most importantly: Beads is built for workflows where agents operate independently for hours at a time. Traditional tools assume humans are constantly available to provide context, make judgment calls, handle edge cases. Beads assumes the dependency graph and task descriptions contain everything needed for intelligent execution.

## Forward vs Backward Dependencies Explained

Here's a real example from my current workflow:

**Forward dependencies** (what this task blocks):
- "draft old posts" blocks "write new articles" 
- "write new articles" blocks "complete content overhaul"

**Backward dependencies** (what blocks this task):
- "complete content overhaul" is blocked by "write new articles"
- "write new articles" is blocked by "draft old posts"

The same relationships, viewed from different directions. But agents care about different views at different times.

When starting work: check backward dependencies. "What's blocking me from starting this?"

When finishing work: check forward dependencies. "What will this unblock when I'm done?"

Beads tracks both automatically. The agent always knows what it can start now (no backward dependencies) and what impact its work will have (forward dependencies).

This bidirectional view is what makes the dependency graph more than just a fancy todo list. It's a workflow state machine. Complete any task, and the machine automatically recalculates what's possible next.

## The Git Integration

Every change gets exported to JSONL:

```bash
$ bd sync
Synced 23 changes to .beads/sync.jsonl
```

This creates a Git-trackable history of every task, every dependency change, every completion. Your workflow becomes version-controlled. You can see exactly what work happened when, how priorities shifted, which dependencies changed.

More importantly: it's distributed. Multiple agents can work from the same bead chain. Changes sync through Git like any other development artifact. The dependency graph becomes a shared coordination layer across your entire AI workforce.

This isn't backup — it's infrastructure. The JSONL format makes the task history queryable, analyzable, reportable. You can generate project timelines, identify bottlenecks, track completion patterns. All from the same data that drives daily execution.
